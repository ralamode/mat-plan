## Goal

One plan for the whole slice, so each of FAM-1's code PRs starts from a settled design instead of its
own plan. It cites the plans it takes from (SCHED-1, ASSIGN-1, V1-22 A4, TGT-1, PICK-1) and takes
**only this slice** of each. It settles everything the milestone and the ADR left to d2: the seven
tracking types (ITEM-1's section), how a logged row is stored, the prescribed-value shape, the
instructions length, the contract shapes that let lanes run in parallel, each lane's files, and the
questions the d3 panel raised.

Each step's PR still owes a short **step note** in its description (what it changes, file by file,
against this plan) and the panel AGENTS.md requires for its kind: a migration gets DB-safety; a screen
gets one UX reviewer, since d3 panelled the design. A step that must depart from this plan **stops first**: the lane tells the maintainer, and the roadmap
thread amends the plan (docs/plans/README.md → "amend it one way"). Lanes do not edit this file.

The milestone's exit criteria, verbatim ([FAM-1 → exit criteria](../milestones/fam-1-family-program.md#fam-1-exit-criteria--done-when)),

| Type          | Label         | Prescribed (D2)                         | One logged row (`entry_sets` + quantities) | Rows            | `entries.unit`  |
| ------------- | ------------- | --------------------------------------- | ------------------------------------------ | --------------- | --------------- |
| `check`       | Check         | nothing                                 | no quantity: done                          | 1               | `bool`          |
| `count`       | Count         | `primary`: value + any unit (`10 lb`)   | `primary`, same unit                       | 1               | its unit        |

- **Every item can be checked off** (R6); ✓ on an untouched row writes the prescription (D13).
- **"Write it" numbers are Count items** (R7). A vest is a Count with a mass unit; structured worn load
  is Beta 1.
- **Each row's other columns** (step 11b proves each against `entries_shape_check`, `schema.ts:376-388`,
  and `entries_activity_type_id_not_null`, 0003:21): `activity_type_id` is one new reference activity
  type, `workout_item`; `movement_id` and **`movement_name` are always set by the row writer** (a Check row has no `value_num`, and `entries_shape_check` then needs the name); `metric_key` is NULL; `kind` is
  NULL. Check-ins, which also write `kind` NULL, must still pass.
- **Types are set once** (D25): built-ins by the step-3 migration, by slug, guarded on the
  `'weight_reps'` default and `household_id IS NULL` (`docs/lessons.md:33-45`); a new item when it is
  made. `findOrCreateMovement` never changes an existing row's type: a new item whose name matches an
  existing one selects that item and shows its type. **"Matches" is `existingItem`'s rule** (contract
  change C8): the name's key or one of the item's aliases, decided before `findOrCreateMovement` is
  reached, so that function is unchanged and only a name that names no item gets to its insert. The
  check is a read before the insert: the slug's unique index still stops two inserts of one name,
  and two calls in the same moment whose names share a key but not a slug (`pushups`, `push ups`)
  can both insert. That is accepted for a household and not serialized.
- **Units** (D27): an item logs in the unit its prescription names; a quantity with no value means
  "log in this unit, no target", and an empty ✓ on it asks for a number.
- **Reference data owed by step 3:** `(primary, count)` in `QUANTITY_SLOT_DIMENSIONS_BY_CODE`
  (`quantity-slots.ts:54`; `(primary, time)` and `(distance, length)` exist); the `workout_item`
  activity type in `catalog-activity-types.ts`; unit `mi` (with its CSV spelling, `csv/value.ts:37`); and ceilings
  for `mi` and `count` in `MAX_QUANTITY_BY_UNIT` (`units.ts:241`), with a test that every `UNIT_CODES`
  member has one (without it every Count row is refused, `units.ts:259`).

**What keeps the lanes apart** (each from [parallel-work](../parallel-work.md)):

- **One mount point per page.** A route file mounts one lane-owned screen with two props: the
  contract's data and the contract's actions object (`ProgramActions`, `DayActions`). Everything a
  later step adds lives inside the screen, so widening a screen never touches a route, and no lane
  waits for another to mount its work. **One exception, the day page (D34):** three parts the
  page places itself (`AthleteSwitcher`, `ProgramLine`, `NotOnAProgram`), because v12 puts them above

  only lane C's own step (12c) places them. The preview harness mounts them the same way; the
  contract owner wires that once 13d has merged, since no lane edits the harness _(maintainer,
  2026-11-16)_.
- **Fakes on the preview route, real actions in production, never a mix.** 0b ships in-memory fakes of
  both actions objects, so a screen is fully clickable on the preview route (`/design/program`, the
  `/design/tokens` precedent) before any table exists. In production a route passes only the real
  actions it has: **an action not wired yet is `undefined`, and the screen hides its control.**
- **Fixtures are tested from both sides.** The screen renders the named fixture; the data lane seeds
  the state the fixture describes and asserts its query, passed through 0c's normalizer, deep-equals it
  (12a-i and 12a-ii, 6a, 6c). A change of mind
  on either side fails that side's own test.
- **Shared append-only files are sharded** (gate 6), all by step 0: database proofs go in
  `verify/{schema,program,day,single-values}.ts`, one per data lane (`verify.ts` is one 10,000-line file today); the
  action registry and its test bindings are composed from one file per action module
  (`mutating-actions.ts:83` and `ACTION_BINDINGS`, `actions.test.ts:251`, are single literals today);
  each UI lane has its own e2e spec; the a11y scan iterates the contract's fixture list.
- **Columns have one owner.** Lanes P and E never edit `schema.ts`. A column this plan missed is a
  **column request** to lane A, added expand-only in its next migration.
- **Start on open, merge on applied.** A lane may write its next step on top of an open PR it is gated
  on (its own, or lane A's migration), as a draft. It merges only when the gate has merged and, for a
  migration, been **observed applied** (gate 3). So the schema chain limits when things land, not when
  they are written.

1280 set. For the 360px side-by-side and any state that needs a tap (a dialog, the picker, a failing

## Risks / rollback

- **The deploy window** (§3): each migration merges when nobody is logging, and the window is accepted
  while nobody uses the app; each step note names the failing statements and the recovery.
- **4b on `prescriptions`:** small-table route, lock up front; rollback drops the constraints, no data
  moves.
- **5b changes the busiest read:** proved byte-identical with a template block present.
- **Twin sessions and rows on replay:** the append and row arbiters, with the typed re-select path.
- **3b-page removes the old forms before the new rows exist** (D29): accepted by the maintainer in
  #412; bodyweight and practice still log, and the household switches only at step 16.
- **Lanes S and E share `write-path.md`, `hide.ts` and the migration queue** (§6): the order is
  written down, and each is one PR at a time.
- **A fake that drifts from the real actions:** both are typed by the same interface and return the
  same `RowResult`; 12c is the early end-to-end test, before the screens are finished.
- **Three shared guides are seams** (§6): a lane that forgets the order collides on the guide gate, not
  in production.
- **Personal data:** each new kind enters the inventory, the notice and both erasure orders in its own
  step.
