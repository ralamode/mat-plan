## Goal

Two defects in Change (13b-ii; live on the day page since 12d, #607):

1. **Escape cancels a Change only from the field.** With focus on the row's ✓, its ✕ or Try again,
   Escape does nothing. The ✕ exists because phones have no Escape key, but a keyboard user on the
   ✕ expects Escape to work as it does in the field.
2. **A ✕ press dragged off loses the edit.** The ✕'s pointer-down sets `cancelling`
   (`use-change.ts:289`) so the field's blur does not send what the ✕ is about to discard
   (`:302`). If the pointer then leaves the ✕ and is released elsewhere, no click comes, `cancelling`
   stays set, and nothing sends the edit until a field is focused again. In Chrome the ✕ also takes
   focus on mousedown, and only a field's blur sends (`onFieldBlur`), so leaving the row from the ✕
   never sends.

## A change to a recorded decision (the maintainer's call)

`docs/features/day-page.md:229`, under "Decided for 13b-ii (maintainer, 2026-11-16)", and the
comment at `apps/web/components/day/use-change.ts:39` say a Change is sent **"when focus leaves the
row from one of its fields"**. This plan sends it when focus leaves the row **from any control**.
That is a change to a recorded decision, not a doc edit, and it brings two saves a person would
notice, both new:

1. **Press ✕, slide off it and lift** (on an iPhone, and in Safari with a mouse): today the number
   stays typed and unsent; this plan **saves** it.
2. **Press ✕ and the page scrolls** (`pointercancel`): today nothing is sent; this plan **saves** it.

**The alternative** for both: the press is called off and the number stays typed and unsent, as
today, with "Not saved. Was …" still showing; only the stuck `cancelling` flag (defect 2's cause)
is cleared, so the next blur out of the row from a field sends it. The panel's UX lens preferred
saving (§ log); the maintainer decides. The PR is a draft that does not merge until they have.

## Acceptance

- Escape from any control in a row whose Change is open (typed over) reverts it. Escape does nothing
  when the row is not being changed, so it never takes another control's Escape.
- Escape from a button that the revert removes (✕, Try again) moves focus to the row's ✓ first, as
  `onCancel` does (`change-parts.tsx:172`); from a field, focus stays in the field.
- **A tap on ✕ cancels, on touch and mouse alike.** Touch order: pointerdown, the field's blur,
  pointerup on the ✕, pointerleave, click. Nothing is sent.
- A ✕ press released elsewhere calls the cancel off. **Pending the maintainer** (above): if focus has already left the row, the edit is
  sent; if it is still in the row, the row stays in Change until focus leaves it.
- A press dragged off the ✕ and back onto it, then released there, cancels.
- Leaving the row from any of its controls (not only a field) sends an open Change, under the same
  conditions as today's field blur: not while a cancel is under way, not to another control in the
  row, not when the window loses focus.

## Test plan

Component tests (Vitest, `fireEvent` in the browsers' orders) as listed. jsdom has no pointer capture and no layout, so `elementFromPoint` is stubbed in the touch tests: they prove the rule, not the browser. **Unverified: iOS Safari's real order and capture.** It is settled by one real-device check (on an iPhone, type over a number, press the ✕ and slide off without scrolling, then lift; and the same with a scroll), owed to the maintainer in the morning and named in the PR, together with the two new saves above. No e2e: the existing one already covers a Change saved by leaving the row.

## Risks / rollback

- **A second send.** The press watch is one-shot, filtered by `pointerId`, and commits only when the
  Change is dirty, not pending, and focus is outside the row. Tested by counting `amendRow` calls.
- **A re-send after a failed save** (S4): leaving the row from the ✓ or Try again now sends the
  open Change again, where 13b-ii sent only from a field. This is intended (an unsent edit is never
  silently kept), and the guide says so.
- **Escape stolen.** It is handled only while the row is dirty, and only from inside the row.
- **Rollback:** revert the PR. Behaviour returns to 13b-ii's.
