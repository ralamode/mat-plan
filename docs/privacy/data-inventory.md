**[notice.md](./notice.md) is the document people read. This file is why it is true.**

Every factual claim in the notice traces to a row here, and every row here traces to code. Derived by
walking `packages/db/src/schema.ts` and the third-party call sites — **not from memory**, which is the
only way a notice about minors' health data is worth anything.

**Re-review triggers.** The standing trigger is `AGENTS.md`'s privacy-lens list and
[review-pr](../../.claude/skills/review-pr/SKILL.md) rubric dimension 10 — the schema, the DAL, an
export, logging, a new dependency, a third-party call. **This file adds three deltas**, which are the
ways this inventory specifically goes wrong:

1. **A new processor**, or a change to what an existing one receives.
2. **A changed vendor retention window** (the three unconfirmed ones below, once confirmed).
3. **A writer appears for a column this file says is unused** — `profiles.birthdate`,
   `profiles.avatar`, `entries.notes`, `day_readiness.note`, `supersets.note`, and (`CAT-3` A1) a
   writer of `movement_equipment` or `movement_muscles` for a household's own movement, or a relaxed
   `movements_household_row_has_no_modality`. "My equipment" (what a household owns, out of `CAT-3`'s
   scope) would be a new data category, owing §1a a row and the notice a sentence. That is the exact
   mechanism by which the notice goes wrong first: not a new column, but an old one waking up.
   ✅ **This trigger has fired three times and worked each time.** `movements.household_id` was listed

**28 tables. TWENTY-ONE are household-reachable** and can hold personal data; seven are reference data. (`workouts` and `block_day_workouts` joined at FAM-1 4a-i, `prescription_quantities` at 4b, `program_assignments` and `program_assignment_weekdays` at 5. ✅ **The count changed at `TEN-2b`, exactly as `TEN-2a` predicted it would** (it read _"becomes
thirteen / five at `TEN-2b`"_). `findOrCreateMovement` now writes `movements.household_id`, so a
`movements` row can be household-authored content and the table moved from §1b to **§1a**. Recorded
before it happened and then actually done — the classification change is the thing that goes wrong
quietly, and this is the mechanism that stopped it.

Every household-reachable table carries `created_at`, `updated_at` and `deleted_at` (`schema.ts` →
`timestamps`), and `deleted_at` is a **soft** delete — see §5. **Except** `movement_equipment` and
`movement_muscles` (`CAT-3` A1), which carry `created_at` only: their rows are written by difference
and deleted hard, with their movement.

✅ **The table set is proved, not only listed** (re-read 2026-11-17, `PRIV-3` PR 1). §1a's twenty-one

and when a table with a `household_id` or `profile_id` column is not in the graph. It proves the set
of tables, not the column descriptions below, which are still checked by a reviewer.

### 1b. Reference data (no personal content)

`units` · `equipment` · `muscles` · `quantity_slots` · `activity_type_categories` · `activity_types` ·
`metric_definitions` — seeded catalogs of codes and labels (`equipment` and `muscles`, `CAT-3` A1, hold
codes only; their labels are in shared code). Nothing about a person, and nothing writes to them from the app,
so they are not deleted when a household is deleted: there is nothing of theirs in them.

🔴 **`movements` LEFT this section at `TEN-2b` — it is now in §1a.** It is the only catalog table with
a user-reachable writer (the free-text movement-name box), and since `TEN-2b` that writer is
**household-scoped**: `findOrCreateMovementId` takes a `HouseholdScope` and resolves **global-first**,
so a name a household types lands in that household's own namespace and **is** deleted with the
household (`runbooks.md` step 11, which `TEN-2a` added for exactly this).

⚠️ **Two claims this section used to make are now false, and one residual replaces them.** It said
there was _"no household scoping"_ and that _"a movement name one household types survives that
household's deletion"_. Both are fixed for names typed **after** `TEN-2b`. ✅ **And the mechanism that
kept minting new ones is gone at `TEN-2c`** — migration `0017` dropped the non-partial
`movements_slug_unique`, so two households can each hold their own row for one slug and the resolver's
`23505` fallback, which handed the second household the first's row, is unreachable.
⚠️ **What survives is the stock, not the flow, and `TEN-2c` did not touch it.** Three shapes still
outlive a deletion, now owned by `TEN-2c-1` and `TEN-2b-2`: a row more than one household references,
a pre-existing app-authored row nothing references, and a row whose only other referencer is a profile
with a NULL `household_id`. All three sit at `household_id IS NULL`, where global-first serves them to
**every** household — that is the **read** leak's residual, and `0017` only stops the set growing (via
`movements_global_row_has_pattern`). `runbooks.md` step 11 lists them; §4 and §8 carry the status and
the retention.

The row's unit and bodyweight flag still carry nothing from the typist — the writer only ever writes
`is_bodyweight: false` and no `unit_default`, which is **why** the resolver is global-first: a
household row would always be a strictly worse version of a curated one
(`packages/db/src/writers/movement-catalog.ts` → `findOrCreateMovement`).

restoring a hidden assignment can fail where a live one took its start or place — and
`uq_household_members_clerk_user`, one live membership per Clerk account, which is a constraint
rather than a slot. ⚠️ **Counted off `0027_snapshot.json`, not off a plan** (superset order's predicate also gained `prescription_set IS NULL` at 0024) (ten at `0021`; the plan once said
nine because it predates the membership index); two further partial uniques key on `movements.household_id` rather
than `deleted_at` and are untouched by any of this.
**What a reader is owed, stated plainly:** a `client_id` can never be reused for a different row,
even after the first is purged — and the "un-deleting can fail" hazard below therefore **does not
apply to `client_id`** on any table. It still applies to the twenty-one slot arbiters above (every partial one but the membership index).

🔴 **Where it started: `PROF-1` a-0 (2026-11-06) built `uq_profiles_client_id` non-partial** — the
first in this database, and the precedent B0 generalised. So for `profiles`, and only
`profiles`, a soft delete does **not** free the natural key, and the "un-deleting can fail" hazard
above does not apply: the slot stays with the athlete who had it, and a retried "add" resolves to
that same athlete rather than minting a second one. ADR 0008 decision 3.4 is the reasoning; the other
fourteen are the shape it argues against, and `V1-9b`'s B0 re-predicates five of them. **The privacy
consequence is a retention one:** a `client_id` is never reclaimed, so the key outlives the athlete's
visibility — it is retained for the row's whole life, like `public_id`, not until deletion.

**This is a description of the code today, not the policy.** [ADR 0008](../decisions/0008-deletion.md)
decides that a per-item delete **hides, then purges at `N`**, and that a hidden row stays **restorable
until it is purged** — so once `V1-9b` and `PRIV-3` land, "stays indefinitely" stops being true and this
section is rewritten with them.

Also: soft-deleting a _profile_ hides it from the picker **and from the export route**, so its data
becomes un-exportable while remaining in the database. Get the export before anything is removed.
⚠️ The export filters soft-deleted rows at **five** places (`packages/db/src/queries/export-month.ts` →
`strengthMonthRows`, `bodyweightMonthRows`, `loggedMonths`), so this is **not** only a profile-level
hazard: once a per-item delete exists, every hidden entry is data we hold and the person cannot export.
ADR 0008 makes _"a hide must never remove the export path"_ a precondition on `V1-9b`.

Two paths actually remove rows: the household deletion in [runbooks.md](../runbooks.md) → "Delete a
household and everyone in it", and, since FAM-1 step 5, "Erase one athlete" (the athlete's profile and
every row that points at it; the household's programs stay).

## 6. Getting data out — and what the export omits

`GET /p/<profileId>/export` returns a zip, per athlete, per month. The directory is the profile's
`public_id`, **never a name**, and **no CSV contains `profiles.name`**. The byte-level contract is
[csv-export-contract.md](../csv-export-contract.md), which owns it; only the privacy-relevant facts
are here.

**What it contains:** the strength log (date, session type, movement, sets, reps, load, prescribed,
notes) and bodyweight (date, weight, context, notes).

**What it does not contain — the notice must say this:**

- **Check-ins and life activities.** The check-ins CSV is written **header-only, always**
  (`apps/web/lib/dal/export.ts` → `buildCheckins([])`), and the month query inner-joins `movements`,
  so a metric or check-in entry reaches **no file at all**.
- `day_readiness.gate_color` · `ramp_targets.target_value` · `sessions.feel` ·
  `profiles.routine_config` · `prescription_targets` (folded only into a derived `prescribed` string).
- **The program a household builds (FAM-1):** `workouts.name`, `description` and
  `copied_from_program_name`, `block_day_workouts.label`. No export reads them, and FAM-1's step 14
  adds only the workout name frozen on a logged session (`sessions.workout_name`, step 4a-ii).
- **A built program's items (FAM-1 4b):** `prescriptions.notes`, `rest_after`, `superset_label`,
  `superset_order`, and all of `prescription_quantities`. The one indirect path: from step 11b a
  target reaches the export only as rendered into `entries.prescribed_snapshot`, for rows actually
  logged; the instructions never do (plan D7). An unlogged program leaves only through the on-request
  full copy. The notice's export-omission sentence does not yet name programs a household builds;
  step 14 owns that sentence (or whichever PR first makes the save reachable, if earlier).
- **A household's own item that no logged entry uses (FAM-1 6a-iii-a):** the export names a movement only through a logged entry, so an item made with "+ New item" and used only in a program, or not at all, reaches no file; the full copy on request has it.
- **Program membership (FAM-1 5):** `program_assignments` and `program_assignment_weekdays`. No export
  reads them; step 14 decides whether the export names an athlete's programs, and owns the notice's
  sentence if it does.
- **Soft-deleted ("hidden") rows.** Every export query filters `deleted_at IS NULL`, so a hidden entry
  is absent from the zip while still held in the database. **User-facing since V1-24 3b-bw:** a
  cleared weigh-in (and from 3b-life-a a cleared practice) leaves the export, and the app offers no restore for it, so the full copy on request
  (which includes hidden rows) is the household's only way to get it back
  ([ADR 0008](../decisions/0008-deletion.md), "a hide must never remove the export path").
- A profile with readiness rows but no entries exports an **empty zip** (`loggedMonths` keys off
  `entries`).

So the export is **the portability answer for logged training, not a full copy.** A full copy is on
request from the maintainer.

outcome. It has carried an **athlete's** public id since TEN-1 (ADR 0006, obligation 3); **since

same rule _(maintainer's decision, 2026-11-16)_. It never carries a name, a logged value, either
household's id, the requester's account id or an internal id, and it is sent only on a miss, so an
id reaches Sentry only when a request for it was refused. **That includes an id of the household's
own that the page does not serve**: a stale link to a program since removed, or an item asked for
an athlete who is not on its program, sends that id at `info` with the outcome `unknown_resource`. Since FAM-1 7a-i, `apps/web/lib/dal/program/report-miss.ts` sends a program or a
workout id: after a rename, a save or the workout editor's read finds nothing, it checks the program
and then the workout against the household and sends at most one event. Since 12b,
`apps/web/lib/dal/day/report-miss.ts` sends a workout or a prescription id: only when a ✓ is refused
`not_found`, it checks the workout and then the prescription and sends at most one event. Retention is Sentry's, in
§8. The alert
that reads it is in [runbooks.md](../runbooks.md) → "A cross-household scope miss".

**Every other Sentry event has public ids masked** (2026-11-16). An athlete's pages put their
public id in the URL path (`/p/<id>`), and the SDK copied it onto each event: the request URL, the
transaction name and Next's `contexts.nextjs.request_path`. Exception messages could carry a row's
`client_id` too. `apps/web/lib/sentry-scrub.ts` now replaces every UUID in every string it scrubs
with `:id`, so an ordinary error report keeps only the route's shape (`/p/:id`). Before this, every
error report from an athlete's page carried their id. The day page's `?d=` query was never sent: the
SDK strips queries, and the scrubber now cuts them too, as a precaution. The scope-miss event above is
the one exception: its id in `contexts.scope_miss.resource` is put back after the masking, on
purpose, and only when it is a well-formed UUID.

present to `verify-full`, and explicitly does not invent one if absent; nothing validates that
`DATABASE_URL` carries it. Whether production is `verify-full` is an environment fact to confirm, not a
code guarantee — it is on the operator checklist in [runbooks.md](../runbooks.md).

## 8. Retention — and the three windows that are not knowable from here

**Program membership (`program_assignments`, FAM-1 5)** is kept as history: taking an athlete off closes
the row and keeps it, and taking them off then putting them back on a later day leaves the closed row and a new one (back on the same day reopens the row, Amendment 4).
Both are kept until the athlete is erased or the household deleted; nothing purges them.

**A built program's items (`prescriptions.notes`, `rest_after`, `superset_label`, and
`prescription_quantities`, FAM-1 4b) are household-scoped, and are NOT removed with one athlete.**
They have no profile column: an instruction or a target written for one child survives that child's
erasure, as `workouts.name` and `description` and a week slot's `label` already do. The runbook's "Erase one athlete" asks the
household, before the cooling-off, about each program only that athlete was ever on (its report query),
and removes it too if they say so. They
go with the household (runbook steps 8a, 9).

**A copied workout (`copyWorkout`, FAM-1 6a-iii-b) is another place a child's instructions and loads live.** A copy is an independent, household-owned set of rows: the source's name and description, every live item's notes, rest note, superset label and reps, and every prescribed quantity (a load, once the program is assigned to one athlete), plus the source program's name frozen in `copied_from_program_name` (which can be "<child>'s program"). Erasing one athlete does not remove a copy: it belongs to the program it was copied into. ✅ **Since PRIV-3 (#561)** the "Erase one athlete" REPORT lists, for each program only that athlete was on, its workouts copied into other programs (part 2), and the household chooses: keep, remove the source and keep the copy, or remove both; step 4b acts on that answer and no longer skips the source silently. Nothing reaches `copyWorkout` until 7a-ii. ⏳ **Owed by 7a-ii:** the notice's sentence (`notice.md`, "if a program was written for that athlete alone") is reworded to say a copied workout is asked about too.

**A household's own item (`movements` with `household_id`, written by the strength form and, from 7a-ii, by "+ New item") is NOT removed with one athlete either.** It has no profile column. Erasing an athlete hard-deletes their entries, and the item stays: since 6a-iii-a the picker lists it whether or not anything uses it, so a label written about one child ("<child>'s knee band") is still listed after that child's erasure. It goes with the household (runbook step 11, a hard delete). ✅ **Since PRIV-3 (#561)** the "Erase one athlete" REPORT lists them (part 3): the household's own items nothing would reference once the athlete is gone, to keep or remove. The app cannot remove an item, so a removal is a correction. An in-place edit overwrites with no history. **What a save hides instead, and keeps until the household is deleted** (since 6a-ii; nothing purges): under plan D19 a **removed** card's row and a **swapped** item's replaced row keep their instructions, rest note, superset label, reps, `client_id` and quantities (a prescribed load among them); a target **cleared** from a kept card is hidden with its value, and re-adding one writes a new row, so hidden targets accumulate; a workout saved **empty** hides every card. A hidden card's id is refused by the next save, so nothing in the app can show, restore, export or erase these rows. ⚠️ The notice's "hidden, not erased" paragraph ties hiding to delete and clear, not to removing, swapping or clearing in the editor; the PR that makes save-workout reachable from a screen (7b) owns that sentence.

**What a week save hides** (`block_day_workouts`, since 6b; nothing purges): a slot taken off a day, or moved to another day, is hidden with its label, and putting the workout back on that day writes a new row, so hidden labels accumulate. No id of a slot leaves the server, so nothing in the app can show, restore, export or erase a hidden one; they go with the household (runbook step 9a) or with a program removed at "Erase one athlete". A relabel overwrites in place, with no history. The notice's "hidden, not erased" sentence for the week is owned by the PR that makes save-week reachable from a screen (7b).

**A session's workout name (`sessions.workout_name`, FAM-1 4a-ii)** is frozen at log time, so a rename never
rewrites history. It is kept for the **session's** lifetime and goes with the session (household
delete step 5; "Erase one athlete" step 4, with the athlete's sessions); it **outlives** the workout's rename,
hide and purge, whose `ON DELETE SET NULL` clears only the id. A session of another household naming
this household's workout must be refused by step 11b's writer (owed, with a boundary test; no session
writer names a workout before 11b) and is flagged by the delete's pre-flight (f).

**A copied workout's source program name (`workouts.copied_from_program_name`, FAM-1 4a-i)** is frozen
at copy time, by design ("Copied from Family program · 14 Nov" must not change when the source is
renamed). So it **outlives** the source program's rename, hide and purge: ADR 0007 Amendment 2 §8
sets the copy's pointer to NULL and keeps the name. Within one household that is the household's own
text. A copy across households is refused twice: by `copyWorkout` (both its lookups go through `liveTemplateBlockIn`) and by `insertWorkoutOwnedBy`'s `copiedFrom` guard (mutation 49; `verify/program.ts` → "household B copying A's workout is not_found"); the household delete's pre-flight (e) flags one
before the delete, because the copy would keep the deleted household's typed name.

🔴 **A prescribed load, once logged against (`entries.prescribed_snapshot`, written since `V1-22`
chunk 2)** — kept for the **entry's** lifetime: a soft-deleted entry hides it, and household
deletion removes it with the entry, so no new deletion step is owed. ⚠️ **It survives any later
edit, soft-delete or supersession of the prescription itself**, which is deliberate — the export
must not change under the reader — but it means a value the household could previously make
disappear by editing the program is now fixed at the moment the set was logged. `''` is a real
stored value (an open prescription renders empty) and NULL means "never snapshotted"; the two are
distinguishable on purpose. ⚠️ **Forward note:** chunk 3's one-time backfill writes `''` for rows it
cannot match (spec R1, upheld 2026-11-11), which makes an already-adult athlete's historical
`prescribed` permanently empty — reversible today, not after the backfill. The ordering that keeps
that harmless is recorded in `docs/features/programming.md` invariant 8: **the backfill runs before
`kind` ever becomes editable.**

🔴 **An archive date (`profiles.archived_at`, written since `PROF-1` b)** — kept until the athlete is
**restored**, which sets it back to `NULL`, or until the household is deleted. ⚠️ **No archive/restore
HISTORY is kept:** the column holds one timestamp, `COALESCE` keeps the FIRST archive date across
replays, and a restore erases it — so the database cannot answer "how many times was this child
archived" or "when were they archived before". That is a deliberate property of a single nullable
column, not an omission, and it is what makes the notice's _"kept in full until you restore them"_
the whole retention statement.

## 9. Personal data committed to this public repository

### The three judgement calls, with reasoning

**1. The exported symbol took a clean break, not an alias.** The second profile's seeded-routine export
is now `SEED_ATHLETE_TWO_ROUTINE`. Every consumer was checked first: three in-workspace sites (the definition
in `packages/db/src/seed.ts`, the re-export in `packages/db/src/index.ts`, and one import in
`apps/web/lib/routine/contract.test.ts`), plus doc mentions. `@mat-plan/db` is `private: true` and has
never been published, so there is no downstream consumer to deprecate for — and an alias would have
**left the name in the public API surface**, which is the one thing the sweep exists to remove. The
A≠B routine contrast the symbol carries is load-bearing and survives unchanged.

**2. The archived program table was scrubbed, not renamed** —
`docs/programs/kids-sc-foundation-archived.md`. It carried four columns (a load and a rep target per
child) across 21 rows: a minor's prescribed training programme. **A rename only de-labels that; the
numbers were the exposure.** Kept: the day split, the order, the movements and the shared prescription —
the part a re-seed actually needs. Dropped: the per-athlete numbers, which that file's own note already
said must be re-confirmed against logged working sets before use, so there was no forward value to trade
against. The shipped `PROGRAM_SEED` already seeds every per-athlete load as `null`, so the scrubbed table
matches how a program is seeded today.

**3. The CSV contract's example rows now quote the cleared corpus verbatim** —
`docs/csv-export-contract.md`, `packages/shared/src/csv/row.ts`,
`apps/web/lib/csv/strength-log.test.ts`. These were **pre-scrub** copies of rows that already exist,
scrubbed, in `docs/samples/legacy-csv/` — the doc was quoting a version of its own evidence file that
the evidence file no longer contains. **Checked before changing them, because they are load-bearing for
the byte-faithful contract**: the property each vector pins is the _bare inch marks in an unquoted field_
(`30" box`), the unescaped comma, `SKIPPED`, `sub-failure` and the slash-list arity — **not** the name or
the date. So aligning them to the committed sample rows preserves every tripwire byte-for-byte while
removing the names, the real dates and the real bodyweight values. No real row is required to pin the
contract; a real _shape_ is, and the shape is unchanged. This is strictly better than deleting the
examples, and it makes the quoted rows checkable against a committed file instead of unverifiable prose.

**Retained with reasons: `docs/plans/v1-10-two-week-program-source.md`.** Its ages and bodyweights are
gone. Its **de-named per-athlete load splits stay**, because they are the evidence for a schema decision
— that `prescription_targets` must be **per profile** rather than per block, since two athletes on one
prescription genuinely carry different loads. Delete the split and the only record of _why_ that table
exists goes with it. This follows the standard the repo already set and reviewed for
`docs/samples/legacy-csv/`: names, dates and bodyweight **values** out, de-named strength loads in. The
difference from decision 2 is that the archived doc is **packaged for re-seeding** (its numbers are an
instruction), while this one is a dated **design record** (its numbers are testimony about shape), and the
file now says so at the top. A stricter call remains available if the maintainer wants it.
⚠️ **Since FAM-1 step 1 no production re-seed path exists** (plan D10: `PROGRAM_SEED` is written only
to test databases). The archived doc stays as the record of a block that may return, through the
program builder or a test seed; its numbers are still an instruction, not testimony.

### What remains — residuals, not oversights

1. 🔴 **Git history.** `git log -S` finds every removed value across the repository's history, and the
   commit author and email are in every commit. Removing it means `git filter-repo` plus a force-push and
   a re-clone, which was **not** in this sweep's scope and remains an open, un-chosen option
   ([plan.md](../plan.md) → `OSS-1` → "The names question").
2. ⚠️ **One occurrence in the working tree, and it stays.**
   `packages/db/migrations/0012_bodyweight_one_per_day.sql` carries a given name in a **comment**. It is an
   **applied** migration: the forward-only guard (`.github/workflows/ci.yml`) permits only **added** files
   under `packages/db/migrations/`, because a migration's SQL is hashed in `__drizzle_migrations` and
   editing it makes prod and the repo diverge. Changing a comment is not worth breaking the one DB rule
   that has no exception. It goes only if history is rewritten, which is residual 1.
3. ⚠️ **The `screenshots` branch.** `prune-screenshots.yml` deletes image files when a PR closes but does
   not rewrite that branch, so earlier screenshots of the picker and Today remain reachable in its history.
   Noted, not acted on.
4. ⚠️ **PR refs #152–#167** still carry a third-party roster of minors that only GitHub Support can purge
   (`OSS-1`).
5. **The production database is untouched, on purpose.** The real names in `profiles.name` are the
   household's own legitimate data, and the seed is `onConflictDoNothing` on `public_id`, so a re-seed
   cannot and does not rename a live row. No correction was written and none is proposed.

**Status:** `OSS-1`'s rename is **done**; the Beta 0 blocker it held is cleared.
